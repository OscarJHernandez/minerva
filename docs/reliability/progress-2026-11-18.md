# Reliability work of 2026-11-18: what was done, what was measured, what is open

This records one working session honestly: what changed, what the live measurements show and do not show, and how
to continue. The target numbers are goals; none of them is claimed as reached unless the table says so.

## Starting point

The latest live reliability run before this work (`reliability-live-after-pr74`) passed 39 of 54 runs. Reading the
code showed why the model-facing parts were weakest, not the engine: routing was one hard-coded rule that skipped
the input pipeline, a verified result was a bare LaTeX string with no assumptions or provenance, the evaluation
scored `load_tools` as a wrong first tool and under-counted tokens of multi-turn cases, and a failed live run left
no trace to replay.

## What changed

Evaluation (PR 81)

- `load_tools` is no longer a wrong first tool; tokens are summed across the turns of a case.
- The report adds per-tool selection and invalid calls, verified-result coverage, model calls per run, multi-turn
  consistency, and the routing setting; `--compare` shows tokens and model calls.
- `scripts/eval_models.py --traces-dir DIR [--traces all]` writes each failed turn as a debug report that
  `scripts/replay_trace.py` reads. Traces hold prompts and model output: the directory is git-ignored
  (`/eval-traces/`) and nothing from a trace reaches a report.
- Two live reliability cases (assumption added then taken back; equations of motion then a conserved quantity) and a
  held-out suite (`--suite heldout`, six cases, not part of `all`).
- Ten Dependabot bumps merged into that branch and their PRs closed.

Routing and input (PR 92, draft, stacked on 81)

- Four new routes next to the Lagrangian one: `followup_reuse`, `ode_analyze`, `matrix_simplify`,
  `lagrangian_followup` (`agent/routing.py`). Each needs structure it can read plus words that ask for the
  operation, takes every argument from what the user wrote, and returns None otherwise.
- A routed call now goes through reference resolution, shape repair, cleaning and the per-call tool context like a
  model call (before it skipped all four), and a rule names the statuses it keeps as an answer.
- Three closed shape repairs seen in the live traces: `symbol` for `name` in matrices, a missing `unknown` when one
  unknown is listed, and the no-op `complex` assumption.

## Measurements

Live runs of the deployed model (`minerva`), `--compute-timeout 10`, seed 7, temperature 0.2, 3 repeats. Reports:
`docs/benchmarks/reliability-live-*.md` and `heldout-live-*.md` (the JSON next to each is the record). The runs
before the routing flag existed had routing off (the evaluation runner never turned it on); their reports say
"not recorded" and the table says off.

| Run | Cases | Routing | Pass | Tool selection | Valid args | Median model calls | False verified |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `reliability-live-before-routes` | 18 | off | 37/54 (68.5%) | 88.9% | 90.0% | 3.0 | 0 |
| `reliability-live-before-routes-rerun` | 20 | off | 39/60 (65.0%) | 85.0% | 92.6% | 3.0 | 0 |
| `reliability-live-after-routes` | 20 | on, 4 routes | 53/60 (88.3%) | 95.0% | 93.1% | 2.0 | 0 |
| `reliability-live-after-routes-2` | 20 | on, 5 routes + repairs | 50/60 (83.3%) | 93.3% | 96.4% | 2.0 | 0 |
| `heldout-live-before-routes` | 6 | off | 9/18 (50.0%) | 66.7% | 88.5% | 3.0 | 0 |
| `heldout-live-after-routes` | 6 | on, 4 routes | 15/18 (83.3%) | 83.3% | 100% | 2.0 | 0 |
| `heldout-live-after-routes-2` | 6 | on, 5 routes + repairs | 18/18 (100%) | 100% | 100% | 2.0 | 0 |

How to read them:

- Routing on is about 18 to 23 points above routing off on the same 20 reliability cases. That is the finding for this suite; on the 161-case core suite the difference is inside the noise (next section).
- The two routing-on runs differ by 5 points and in which cases fail. Run-to-run noise is about that size, so
  neither is "the" number. One model, 3 repeats per case, 54 to 60 runs: a direction, not a rate.
- The 90% pass target and the 99% valid-argument target are **not met**. Tool selection reached 95.0% in one run
  and 93.3% in the other; the 95% target is met at best marginally.
- The held-out 100% is not independent evidence. The rules and the cases were written by the same author, and
  `lagrangian_followup` was added after the held-out pendulum case was seen failing (its trace was not read). The
  4-route figure of 83.3% is the cleaner one.
- The first two rows are not comparable to each other beyond noise: the second adds the two new reliability cases,
  which fail without routes.
- Offline results (`eval_offline.py`) use a replayed model and say nothing about live reliability. They are
  unchanged by this work (no trajectory touches the new routes).

## The core suite (161 cases, live, one run each)

Run after the routes were built, to see whether the reliability-suite gain holds on the broad suite (`core-live-routing-off`
and `core-live-routing-on` in `docs/benchmarks/`; same model, seed 7, `--compute-timeout 10`, one repeat, 148 scored
runs, 13 informational cases excluded; code `e5f9a50`).

| Run | Pass | Tool selection | Valid args | Completion | False verified | Median model calls |
| --- | --- | --- | --- | --- | --- | --- |
| routing off | 85/148 (57.4%) | 81.1% | 79.4% | 91.2% | 0 | 2.0 |
| routing on | 87/148 (58.8%) | 82.4% | 79.5% | 90.5% | 0 | 2.0 |

What this says, and does not:

- **The reliability-suite gain does not carry over.** Routing moves the broad suite by 1.4 points on one run, which is
  inside the noise (about 5 points on the smaller suite). The routes cover a few specific shapes; most of the core
  suite never meets one. The 88% / 83% figures above describe the reliability suite only and must not be read as
  Minerva's overall reliability.
- **Overall reliability is far from the targets**: 58% pass, 82% tool selection, 79% valid arguments (46 of 224
  calls invalid). The earlier reliability numbers flatter the system because that suite was built around known
  failures.
- **Failures cluster** (routing-on run). By failure class: tool selection 22, honesty 13, unproductive loop 12,
  arguments 10. By category: unsupported 0/10, false claims 5/14, physics 19/35, calculus 19/31. By tool:
  `statistical_mechanics` fails 9 of 9 runs with 19 of 27 calls invalid, `creative_telescoping` 3 of 3 (10 invalid
  calls), `vector_calculus` 12 of 17.
- **What the invalid calls were** (read from the exported traces of failed turns): `integrand` sent where the tool's
  formula field is `latex` (telescoping); numbers in `fields[].components` where the tool takes text (vector); a
  `statistical_mechanics` `system` built from invented field names (`E`, `g`, `n` instead of `energy`, `degeneracy`,
  `index`), which no closed repair can fix; `matrices` without `name`; a `distribution` call with no formula at all.
  The first two are repaired by closed rules (next section); the rest need the model to be asked again, or a
  better tool description.
- **The "unsupported" category fails 10 of 10 for mixed reasons** (the model not calling the tool 3 times, a wrong
  tool 2, reply wording 3, loops after invalid arguments 2; classes from the traces' failure notes): the correct behaviour there is an honest refusal in the reply, and
  the model rarely writes one in the words the checks require. This is the largest single category to study next.
- **The two repairs, measured on the 29 affected cases** (telescoping, vector calculus, electromagnetism,
  distributions; `core-live-subset-after-repairs`, same seed, one run): invalid calls fell from 20 of 66 (30.3%) to
  10 of 61 (16.4%), `creative_telescoping` from 10 invalid calls to 1. The pass count moved from 9 to 10 of 29
  (3 cases newly passing, 2 newly failing), which is noise: removing invalid calls did not make those cases pass,
  because most of them fail for other reasons (the mathematical result checks, honesty, loops). A fix that
  reduces errors is not the same as a fix that raises the pass rate, and this one has only shown the first.
- One run per case: single failures are not conclusions. The informational cases and the multi-turn metrics are
  absent from this suite (no follow-ups in `cases.yaml`).

## What is still failing

From the traces of `reliability-live-after-routes-2` and the earlier runs (not committed; they are local):

- Two honesty cases, unchanged by any route: after `integrate` returns `not_verified` the model writes claims about
  divergence and unchecked formulas (`oscillating-integral-stops-when-not-verified`); after `differentiate` refuses a
  functional it asks questions instead of saying it is unsupported
  (`derivative-of-a-functional-is-refused-not-improvised`, flaky). The planned fix (engine-written replies behind a
  flag) would not reach them, because their calls are not routed, so it was not built.
- The model sometimes does not call `simplify` at all for a plain "Simplify ..." request (at least one run of the last run; I did not count the repeats).
  The baseline had it choosing `simplify`, `differentiate` and `integrate` correctly, so no route was added; one
  occurrence is not enough to justify one, but it is the first thing to watch.
- Wording: in the last run the oscillator follow-up failed its `reply_forbids` check (a pattern that guards against
  claiming the search is complete). The route made the call; I did not read the reply, so the cause is not established.
- Invalid arguments are 3.6% of calls (96.4% valid). `action: "expand"` for `matrix_calculus` is the one pattern
  seen and not repaired, because mapping it to `simplify` would be a guess.

## Not done

- Verified results are still LaTeX strings in `ResultStore`. The typed `ResultRecord` (tool, assumptions,
  restrictions, evidence, dependencies), assumptions travelling with `@rN`, and `@rN` inside list fields were
  planned and not started. `lagrangian_followup` reads the Lagrangian from the previous turn's call instead.
- Retrieval (identity recall@1 29%, distributions 6.9%), chat result actions, the shared outcome vocabulary for
  method suggestions, splitting `tools.py`, and property tests for approximation, statistics, distributions, series
  and telescoping.
- The conversation list shows "Rename" on every row. Planned: rename by double-click or F2 with a hover or
  focus-revealed pencil, and the same for delete. Not implemented.
- Vector calculus and distributions are deliberately not routed.

## How to continue

The loop that found every fix above, using only what is already in the repository:

1. Run live with traces: `scripts/eval_models.py --base-url ... --models ... --suite reliability --repeat 3 --seed 7
   --compute-timeout 10 --label NAME --traces-dir eval-traces/NAME [--traces all]`. The host comes from the
   command line or `MINERVA_EVAL_BASE_URL` and is never written to a report.
2. Read each failed turn (arguments the model wrote, tool outcome, reply) and classify it: the model, the tool, or
   the harness. `scripts/replay_trace.py REPORT` re-runs the recorded calls against the engine and tells the first two
   apart; `--llm` replays a whole turn without a model.
3. Pin every reproducible failure as an offline test (a trajectory in `evaluation/offline.py`, a case in
   `cases_reliability.yaml`, a wrong twin in the test that covers the rule) before fixing it.
4. Fix, then run again on the same cases, model, seed and repeats, and compare with `--compare`. Do not read the
   traces of `--suite heldout` to fix a case: pin the cause with a new visible case instead, or the suite stops
   measuring generalisation.
5. For real use, `scripts/diagnostic_codes.py` on the API's JSON log ranks which tools fail most often without
   any content in the log.

Method notes that cost time and are worth knowing: the corruption report and the verification summary both count
evaluation cases, so adding a case means regenerating them (`scripts/eval_corruptions.py --json-out ... --out ...`,
`scripts/verification_report.py`) or CI fails; a script that runs the engine from stdin fails in the sandbox's
spawn (use a file with `if __name__ == "__main__":`).
